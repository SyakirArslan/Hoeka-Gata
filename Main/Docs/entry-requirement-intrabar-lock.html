1. Kenapa draft ini ada

RecalculateEngulfing() me-replay seluruh histori pada setiap tick dan tidak menyimpan state di antara tick. Pola hanya sah bila DetectEngulfing() lolos pada bar itu, dan syaratnya memakai harga close (close > high(S−1) untuk BUY). Di dalam candle yang masih berjalan close adalah harga terakhir, sehingga:

  • tick 1..n: harga melewati high(S−1) → pola dianggap sah → label PENDING tampil, alert BREAK BODY terbit, ENTRY tersentuh → alert ENTRY FILLED (EA shift 0 sudah membuka posisi);
  • close S: harga berbalik dan close(S) ≤ high(S−1) → syarat engulf gagal → blok CREATE tidak berjalan → level, garis, label, panel, dan buffer EA hilang, karena replay berikutnya tidak pernah tahu setup itu pernah ada.
Inilah yang di dokumen lama disebut “pola gugur saat close” (skenario VOID). Setelah skenario C dihapus dari entry-animation.html, animasi tidak lagi menampilkan kejadian ini — sementara engine masih melakukannya dan Docs/Indicator_MT5.md masih mencantumkannya sebagai batasan. Draft ini yang menutup selisih tersebut.

R2.7 Masa hidup kunci kunci tidak dihapus saat setup selesai (replay berikutnya masih membutuhkannya untuk merekonstruksi histori); tabel tumbuh mengikuti jumlah bar yang pernah punya setup intrabar, tanpa batas dan tanpa pembuangan entri tidak ada kebocoran memori yang berarti (EngulfLock hanya 6 angka + waktu, satu entri per bar yang punya setup) dan histori tetap deterministik; pencarian memakai binary search karena tabel urut menurut waktu bar
R2.8 Visual tidak berubah gaya setup hasil pemulihan garis/label yang sudah digambar di dalam candle S tetap; saat TP/SL kena, aturan FREEZE berjalan seperti biasa
R2.9 Level beku selama kunci untuk bar itu ada, BREAK BODY / ENTRY / SL / TP tidak dihitung ulang angka yang tampil setelah close = angka yang diumumkan alert. EngulfAtrAt(i) ikut memakai bar S, jadi ATR berubah dari range sementara ke range final saat candle close; tanpa aturan ini entry/SL/TP bisa bergeser - dan fill yang sudah terjadi bisa batal - hanya karena candle-nya tertutup
R2 hanya aktif bila InpAllowFormingBar = true (lihat D10). Dengan default false tidak ada setup intrabar, jadi tidak ada yang perlu dikunci dan perilaku v2.03 tidak berubah sama sekali.

4. Perubahan kode minimum

Sudah diterapkan di HoekaGataIndicator_Core.mqh (v2.04). Nomor baris di bawah mengacu ke build v2.03 sebelum perubahan. Semua tambahan hanya berjalan bila InpAllowFormingBar = true, jadi build default tidak berubah perilakunya.

  1. Tabel kunci + helper, di atas RecalculateEngulfing() (setelah EngulfComputeLevels): struct EngulfLock, EngulfLockFind() (binary search), EngulfLockStore(), EngulfLockMarkFilled(). Menyimpan level setup yang lahir di candle berjalan, supaya replay berikutnya tidak perlu mengenali pola lagi.
  2. Deteksi (baris 324–327). Cari kunci untuk time[i]; bila pola sudah tidak lolos tapi kuncinya ada (lockedBar), bar itu tetap dihitung sebagai sinyal (stats.nSig++).
  3. Blok CREATE (baris 359, 434–441). Syarat ditambah lockedBar, arah selalu diambil dari kunci bila ada, dan keempat level diambil dari kunci tanpa memanggil EngulfComputeLevels() (R2.9). Setelah state = dir: simpan kunci (R2.1) dan, bila filled, langsung jadikan ACTIVE + tulis buffer (R2.3).
  4. Blok fill (baris 560, setelah fill SELL). Tiga baris untuk menandai kunci sudah terisi (flags.hitBuy || flags.hitSell). Tidak ada perubahan pada blok fill BUY/SELL.
  5. Tidak ada perubahan pada blok cancel (568–591), aturan “tanpa break body” (598–602), FREEZE, gerbang alert (726–727), panel, dan Drawing.mqh.
// ===== v2.04 - kunci setup intrabar (R2) ===================================
// RecalculateEngulfing() dihitung ulang dari awal pada setiap tick dan tidak
// menyimpan apa pun, jadi tabel inilah satu-satunya memori antar tick.
struct EngulfLock
{
   datetime barTime;
   int      dir;
   double   pBreak;
   double   pEntry;
   double   pSL;
   double   pTP;
   bool     filled;
};

EngulfLock g_engulfLocks[];          // urut naik menurut barTime, tanpa batas

int EngulfLockFind(const datetime barTime)          // binary search (R2.7)
{
   int lo = 0;
   int hi = ArraySize(g_engulfLocks) - 1;

   while(lo <= hi)
   {
      int mid = (lo + hi) / 2;

      if(g_engulfLocks[mid].barTime == barTime)
         return mid;

      if(g_engulfLocks[mid].barTime < barTime)
         lo = mid + 1;
      else
         hi = mid - 1;
   }

   return -1;
}

void EngulfLockStore(const datetime barTime, const int dir,
                     const double pBreak, const double pEntry,
                     const double pSL, const double pTP)
{
   if(EngulfLockFind(barTime) >= 0)
      return;

   int size = ArraySize(g_engulfLocks);
   ArrayResize(g_engulfLocks, size + 1);

   int at = size;                               // bar baru selalu paling akhir
   while(at > 0 && g_engulfLocks[at - 1].barTime > barTime)
   {
      g_engulfLocks[at] = g_engulfLocks[at - 1];
      at--;
   }

   g_engulfLocks[at].barTime = barTime;
   g_engulfLocks[at].dir      = dir;
   g_engulfLocks[at].pBreak   = pBreak;
   g_engulfLocks[at].pEntry   = pEntry;
   g_engulfLocks[at].pSL      = pSL;
   g_engulfLocks[at].pTP      = pTP;
   g_engulfLocks[at].filled   = false;
}

void EngulfLockMarkFilled(const datetime barTime)
{
   int k = EngulfLockFind(barTime);
   if(k >= 0)
      g_engulfLocks[k].filled = true;
}

Catatan implementasi: kunci menang atas pola. Selama entri untuk bar itu ada, arah dan level selalu dari kunci - termasuk bila close berbalik sangat jauh sampai bar yang sama memenuhi syarat arah berlawanan, karena setup yang sudah diumumkan tidak boleh diganti diam-diam. Blok cancel (568/581) tidak berubah: memakai close[i] dan notFormingBar, sehingga R2.4 keluar tanpa kode baru. R2.5 bisa dibuktikan: untuk BUY, close > ENTRY berarti high(S) >= ENTRY, jadi pending pasti sudah terisi di bar S - setiap kunci berakhir filled atau canceled, tidak ada cabang ketiga.

5. Acceptance criteria

#Skenario ujiHasil yang diharapkan
1 Filled lalu close gagal. Candle S live: high melewati BREAK BODY, lalu menyentuh ENTRY, lalu harga berbalik dan close di bawah high(S−1) Panel tetap BUY, garis ENTRY/SL/TP tetap, buffer EA terisi, TP/SL di bar berikutnya tetap dievaluasi; tidak ada alert tambahan (tidak ada CANCELED)
2 Armed lalu close gagal. Sama seperti #1 tetapi high(S) tidak pernah menyentuh ENTRY Saat close: alert ENTRY BUY CANCELED, panel NONE, semua garis setup hilang; bar berikutnya yang menyentuh ENTRY tidak mengisi order
3 Tanpa kegagalan. Candle S live menyentuh ENTRY dan close-nya tetap di atas high(S−1) Identik dengan v2.03: BREAK BODY lalu ENTRY FILLED, panel BUY; kunci tidak berpengaruh
4 Counter. Bandingkan panel sesaat sebelum close S dan sesudah close S pada skenario #1 Signals dan Runs tidak berubah angkanya (R2.6); yang berubah hanya bila memang ada event baru
5 Re-attach / ganti timeframe saat candle S masih berjalan (D9 = A) Kunci hilang, bar dinilai ulang dengan close saat itu; bila pola gagal, setup tidak muncul (perilaku v2.03). Ini batasan yang didokumentasikan, bukan bug
6 Regresi. InpAllowFormingBar = false (default), jalankan acceptance R1 #1–#7 Semua hasil sama persis dengan v2.03; tabel kunci tidak pernah terisi
7 Level beku (R2.9). Catat ENTRY/SL/TP yang tampil intrabar, lalu bandingkan tepat setelah candle S close (skenario #1 dan #3) Angkanya identik, sama dengan isi alert BREAK BODY … pending entry …; garis tidak bergeser dan fill tidak batal karena ATR berubah ke range final
Keputusan final: D8 = A, jadi buffer EA tetap diisi untuk setup terkunci dan EA berperilaku sama dengan yang dilihat user. Bila suatu saat D8 diubah ke B, acceptance #1 berubah menjadi “garis/panel tetap, buffer kosong sehingga EA tidak entry”.
